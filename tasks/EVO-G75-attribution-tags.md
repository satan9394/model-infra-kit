# EVO-G75 — 让宿主看清「哪个功能在烧钱」：可选的调用归属标签

> 暂存于 `.tmp/`，待转正。**来源**：独立竞品调研 D2（`.tmp/competitor-refresh-2026-09-11.md` §5 D2）+ 编排者综合（`.tmp/competitor-synthesis-R155.md` §2，编排者裁决 **P2**，研究者原评 P1）。
> 覆盖 GAP：**G75**

## 目标

宿主在自己的进程里，能给每次模型调用**打一个自己的标签**（如 `feature=quant-backtest`），并据此在 `usage summary`/`export` 里**按业务维度切分成本**。

## 用户场景

本产品的宿主是「任意 AI / CLI / 量化项目」。**同一个宿主里往往有多种业务共用一套模型层**——现在只能按 provider/model 聚合，看不到「哪个功能在烧钱」。

嵌入库在这里有**天然优势**：宿主的代码就在同一进程里，拿到标签**不需要虚拟 key、不需要多租户**（这也是它与 LiteLLM「需要 key/team 表」方案的分别）。外部证据：
- LiteLLM 为「把 batch 成本归属到创建者 key/tags」专门加了两列 migration，因为**无归属的成本行会被 DB 直接丢弃**（[#34456](https://github.com/BerriAI/litellm/pull/34456)）
- vercel/ai [#19668](https://github.com/vercel/ai/issues/19668) 指出 "telemetry and billing consumers therefore undercount delegated runs"

## 当前问题

- 请求路径上没有承载宿主自定义标签的位置；
- 用量行只有 `app_id`（**一库多 app** 的维度，不是**一 app 多业务**的维度）；
- 因此「同一 app 内按功能切分成本」**在当前数据模型下无法表达**。

## 理想行为（**必须最小**）

1. `generate()` / `stream()`（以及 `mik.fetch`，若适用）接受一个**可选**的标签参数，形如 `metadata: { feature: "quant-backtest", sessionId: "..." }`——**字符串键值**，键值均由宿主定义，**本模块不解释其语义**。
2. 标签**落库**，并可在 `usage summary`（分组）与 `usage export`（列）中体现。
3. **完全可选**：不传 = **行为与现在逐字一致**（这条是硬约束，见「不能破坏什么」）。
4. **不做权限、不做多租户、不做配额**：标签只是**字符串归属**，不是身份。**任何基于标签的访问控制都不属于本卡**。

## 涉及模块

`src/types.ts`（请求/用量类型）、`src/hub.ts`（请求路径 → 用量行）、`src/store/schema.ts`（**迁移**）、`src/store/usage-repository.ts`、`src/usage/`（查询与导出）、`src/cli/commands/usage.ts`、`docs/interfaces.md`（**必须同步**，硬性规则 5）、`docs/SPEC.md`（若涉及公开类型语义）

## 不能破坏什么

- **不传标签时行为逐字不变**（含 `usage summary`/`export` 的既有行与列顺序）。→ 必须给对照证据。
- **`usage export` 的既有 CSV 表头不得改变语义**：新增列只能是**追加**；既有列名与顺序不变（外部脚本契约）。
- **金额仍以整数微美元累加**（硬性规则 2）。
- **密钥不落库**（硬性规则 4）：标签是**宿主自定义字符串**，**必须排除**把它当作可用凭据通道的用法（例如不得影响 `api_key_ref` 解析）；并且标签会进 CSV/日志 → **必须经 `redact()`**（宿主可能不小心把 token 放进标签）。
- **迁移必须向后兼容**：旧库升级后**不得丢数据**；无标签的既有行应能正常读出（`NULL`/空标签）。
- 既有 **510+** 例测试全绿；`tsc --noEmit` 0；CI 三 OS 绿。

## 验收标准

- **A1**：打标签调用 → 该用量行可查回同样的标签；`usage export` 的 CSV 含该标签列。
- **A2（反向）**：**不打标签**调用 → 输出与改前**逐字一致**（既有列、既有行）。
- **A3（分组）**：`usage summary` 能按标签分组给出成本（或明确给出「如何按标签切分」的既有能力入口——**若不加分组渲染，须说明理由**）。
- **A4（迁移）**：**用改前版本建的库**（可先 `git stash` 前的产物建一个，或手工建旧 schema）升级后：① 不丢数据；② 旧行读得出；③ 新行可写。
- **A5（契约）**：`docs/interfaces.md` 已更新，且**用 `dist/index.mjs` 的实际导出名核对**。
- **A6（脱敏）**：构造一个「标签里含 token 形状字符串」的用例，断言 CSV/日志中**已被脱敏**。
- **A7**：`tsc` 0；全量测试在 **zh-CN 与 en-US** 下均全绿；`e2e` exit 0；`check-envs` 三环境 PASS；CI 三 OS 绿。

## 错误场景

- 标签键值含超长字符串 / 非字符串（数字、`null`、嵌套对象）→ **不得抛异常**（不阻塞宿主，硬性规则 6），应按既定策略处理（忽略 / 字符串化）并**在报告写明**。
- 旧库无该列 → 迁移必须补列。
- 标签键名与既有列冲突 → 需明确策略。

## 测试要求

- ≥7 新用例：① 标签可查回；② 不打标签时逐字不变；③ 分组成本；④ **旧库迁移不丢数据**；⑤ 契约与实际导出一致；⑥ 脱敏反例；⑦ 异常标签值不抛错。
- 全部注入 `MIK_LANG`；**不得**读真实 locale。
- **G43 自检**：每条断言在改前必须能红。

## 为何是 P2 而非研究者主张的 P1（编排者裁决，须保留理由）

价值真实，但**它改动公共 API 与数据模型**：按本仓硬性规则 5 必须**同时更新 `docs/interfaces.md`**，且需要 **SQLite 迁移**（A4 的向后兼容是真正的工作量）。→ 成本明显高于 G73（加一个枚举值）与 G74（纯展示既有数据），故排在其后。
