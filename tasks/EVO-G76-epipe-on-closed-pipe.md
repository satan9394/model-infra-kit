# EVO-G76 — 管道被提前关闭时 CLI 不该崩（EPIPE）

> 来源：**编排者独立发现**（R181，用**已发布 0.2.14** 复现，确认是**既有缺陷**，非 G74 引入）。
> 覆盖 GAP：**G76**（编排者定 **P2**）

## 目标

`mik` 的任何输出被**下游提前关闭**时（`| head -1`、`| grep -q`），**进程正常退出**，不再以 EPIPE 崩溃成退出码 1。

## 用户场景

```
mik usage logs | head -20
mik usage summary | grep -q "Requests" && echo ok
mik models list | head -5
```
这类**管道用法是命令行的日常**。但实测：在 `set -e` 或 `set -o pipefail` 的脚本里，**整条命令会失败**——用户会以为「mik 坏了」或「查询出错」，实际上查询本身完全正常。

**这与 G74 直接相关**：G74 让 `usage summary` 的输出变长，于是电池里 `cli | grep -q "Requests"` 这个既有的脆弱管道**从「偶发」变成「确定性失败」**，把该缺陷暴露了出来（电池那处已被改为落盘再 grep，**但那只是绕开，不是修复**——见 §「与 G74 的关系」）。

## 当前问题（编排者 R181 实测，WSL bash）

| 命令 | 退出码 |
|---|---|
| `usage summary \| head -1` | **1** |
| `usage logs \| head -1` | **1** |
| `--help \| head -1` | **0** |

- 在**已发布的 0.2.14**（G74 之前）上同样如此 → **既有缺陷**。
- `--help` 之所以幸存，推测其输出能在**一次 write** 内写完（未触发后续写入）；而多行输出在管道关闭后再写就触发 `EPIPE`。

## 理想行为

1. **检测 `EPIPE` 并正常退出**（退出码 0）——当 stdout 的下游已关闭时，「没人再读」不是错误。
2. **不得吞掉其它 I/O 错误**：只处理 `EPIPE`（`code === "EPIPE"` / `errno === -32`），其它写错误**仍须**按既有语义报错并给出非零退出。
3. **不得改变正常路径的任何字节**：完整读取时输出与退出码**逐字不变**。
4. **覆盖所有会多行输出的命令**（`usage summary/logs/trends`、`models`、`pricing list`、`provider list`、`--help` 等）——**不要只修 `usage summary`**（这是 G14/G58 那类「只修被看见的那一个」的教训）。

## 涉及模块

`src/cli/`（**输出入口**——若存在统一的 `io.out`/`io.err` 抽象，应**在那里**统一处理，而不是每个命令各写一遍；请先查清是否存在该收敛点）、`bin` 入口的顶层错误处理、可能 `src/cli/index.ts` 的 `main()`。

## 不能破坏什么

- **正常路径逐字不变**（含退出码）。→ 必须给对照证据。
- **既有错误语义不变**：缺参数/未知命令/未知选项/凭据缺失等仍须**非零退出**且文案不变（**冻结面** `cli-english-surface.test.ts` 5/5 必须仍绿）。
- **不得用「全局吞掉所有写错误」实现**（那会把磁盘满、管道断开以外的真实故障一起吞掉）。
- 既有 **544** 例测试全绿；`tsc` 0；字典对等（当前 **294**）。

## 验收标准

- **A1**：对**至少 3 个多行输出的命令**（含 `usage summary`、`usage logs`、`models`）断言 `| head -1` 时**退出码为 0**。
- **A2（反向，最重要）**：构造一次**非 EPIPE 的写失败或正常错误路径**（例如未知命令），断言**仍然非零退出**且文案不变 → **证明你没有把错误一起吞掉**。
- **A3**：完整读取时输出与退出码**与改前逐字一致**（对照基线：**从已发布 0.2.15 产物**抓，别用可能陈旧的 `.tmp/baseline-*`）。
- **A4**：冻结面 `cli-english-surface.test.ts` **5/5 绿**。
- **A5**：`tsc` 0；全量测试在 **zh-CN 与 en-US** 下均全绿（基线 **544**）；`e2e` exit 0；`check-envs` 三环境 PASS；CI 三 OS 绿。
- **A6（可选但建议）**：把**电池**里那处「落盘再 grep」改回普通管道（`cli | grep -q`）——因为修好 EPIPE 后它应当能直接通过。**这会把被 G74 移走的那个检测补回门禁**（见下）。

## 错误场景

- 下游在**第一行之后**才关闭（最常见的 `head -1`）→ 后续写入 EPIPE。
- 下游在**写入过程中**关闭（`head -c 10`）→ 部分写入后 EPIPE。
- 下游**从未读取**（`> /dev/null` 后立即退出）→ 同上。
- `stderr` 被关闭（`2>&1 | head -1`）→ **也要处理**，否则仍会崩。

## 测试要求

- ≥5 新用例：① 3 个命令的 `head -1` 退出码 0（A1）；② 非 EPIPE 错误仍非零（A2，**必须能红**）；③ 完整读取逐字不变（A3）；④ stderr 被关闭的场景；⑤ 若在统一 `io` 层实现，加一条**「所有命令都走该层」**的结构断言（防将来新命令绕开）。
- 测试请**注入/构造管道关闭**，不要只跑 shell（vitest 里可通过写到一个已 destroy 的 stream 模拟）。
- **G43 自检**：每条断言在改前必须能红（**改前 `| head -1` 退出码就是 1，A1 天然会红**）。

## 与 G74 的关系（**必须保留**）

G74 的实现者把电池里的 `cli | grep -q "Requests"` 改为「落盘再 grep」。**独立 Evaluator 指出**：`battery.sh` 顶部是 `set -euo pipefail`，所以旧写法**原本确实会拦住 EPIPE**——改完后**电池再也发现不了这个缺陷**。当时判为**可接受的「有记录的归口转移」**，**前提是 G76 保持登记**。
→ **本卡完成后，A6 应把那个检测补回电池**（改回普通管道）；**若本卡被撤销，则必须回退 `battery.sh` 那一行**。

## 范围外

G70（输出噪声）、G71（文档入口）、G72（电池失败时的诊断退化）、G75（归属标签）、G77（`pricing_source` 进 rollup）。**不要**在本卡顺手改任何命令的输出内容（只改「写失败时怎么办」）。
